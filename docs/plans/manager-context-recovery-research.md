# Manager: 여러 작업 감독과 컨텍스트 복원을 위한 UX 조사

- 작성일: 2026-10-03
- 상태: 사용자 목적 재정의에 따른 조사 초안. 독립 검토와 사용자 합의 전이며 구현 계획이 아니다.
- 이전 기록: [작업 단위·구조 조사](manager-ux-research.md)
- 기존 [더미](../prototypes/manager-workspace.html)는 사용자가 목적에 맞지 않는다고 평가한 비교 대상이다. 승인된 화면으로 사용하지 않는다.


## 인터랙티브 더미 · 2026-10-06

사용자 요청에 따라 [mast 화면 기반 워크플로우 더미](../prototypes/manager-context-workflow.html)를 추가했다. 브라우저에서 파일을 열면 별도 설치 없이 동작한다. 실제 제품 구현이나 설계 승인을 의미하지 않는다.

- 전체 브리핑에서 작업 목적, 내 마지막 결정, 이후 변화와 현재 판단 사항을 읽는다.
- 검색 개선 작업을 열어 질문 → 내 결정 → 실행·검증 경과와 원문을 확인한다. 기존 방향 유지 또는 Redis 검토로 변경을 선택한다.
- 상단 **다음 상황 재생**을 두 번 눌러 전송 시도 → 수신 확인 → 후속 보고를 확인한다. 새 지시 원문은 전달 기록에 즉시 남고, 상단 마지막 결정 요약은 후속 보고 시 반영된다.
- 이미지 업로드에서는 구현 완료와 남은 검증을 구분하고, CSV 작업에서는 오래된 보고 갱신 후 새 판단 사항을 확인한다.
- 하단에서 Manager에게 전체 작업을 묻거나 개별 팀장에게 입력한다. 추천 질문과 선택지만 사전 작성된 시나리오로 응답한다. 자유 입력은 원문 전달 단계를 보여주며 실제 AI 실행 결과를 만들지 않는다.
- 사이드바에서 pane 더미로 이동하고 작업 보고로 돌아올 수 있다. 새 워크스페이스는 담당 미지정 상태로 추가된다. 기존 pane 연결·담당 지정 자체는 이번 더미 범위에 포함하지 않았다.

JavaScript 구문 및 DOM 상호작용 검증에서 결정 분기, 전달 단계, 검증 범위, 갱신 후 질문, 확인 표시, 새 워크스페이스, pane 이동과 초기화를 확인했다. 실제 브라우저의 시각 검수는 완료하지 않았다. HTML로 정보 구조·탐색·결정 흐름을 평가할 수 있지만 요약의 정확도, 실제 전달 성공, 여러 에이전트의 동시 갱신 성능은 별도 연동 검증이 필요하다. 데이터는 메모리에만 유지되며 새로고침하면 초기화된다.

## 1. 성공해야 하는 사용자 업무

사용자는 여러 개발팀을 감독하는 본부장에 해당한다. 각 워크스페이스의 메인 오케스트레이터는 해당 작업을 책임지는 팀장처럼 쓰이고 있다. Manager가 총괄 팀장처럼 각 팀의 상황과 의사결정을 취합하는 역할을 맡는 것이 적절한지는 이번 조사 대상이다.

사용자가 한 작업에 다시 주의를 돌렸을 때, 왜 시작했는지와 이전 지시·질문·결정을 재구성하는 부담을 줄여야 한다. 첫 보고에서는 for/if 같은 구현 세부사항 대신 목적, 방향, 중요한 선택, 그에 따른 실행, 현재 검증 상태가 필요하다. 필요할 때는 판단의 근거와 실제 작업 내역으로 내려갈 수 있어야 한다.

이전 더미는 상태·마지막 답변·일반 이력을 나열하는 데 치우쳤다. 같은 정보가 존재하더라도 사용자가 별도 탭에서 읽고 연결해야 한다면 복원 부담이 남는다. 화면의 작업 수나 요약 길이만 줄이는 것으로 목적 달성을 판단하지 않는다.

### 합의 유지 및 새 설명의 경계

- 개인용 MVP, 우선 워크스페이스 1개 = 작업 1개, 기존 작업과 수동 추가 pane 연결은 유지한다.
- Manager의 작업 생성·입력 전달·맥락 조회·후속 행동 제안, 사용자의 우선순위·중단 결정은 유지한다.
- “팀”은 역할을 설명하는 비유다. 별도 조직·팀 객체나 모든 워크스페이스의 추가 팀장 에이전트를 만들기로 합의한 것은 아니다.
- 사용자는 각 작업 단위가 유동적일 수 있다고 했다. 지금 별도 조직 계층이나 자동 재분류를 도입하지 않는다.
- Manager = 총괄 팀장, 메인 에이전트 = 개별 팀장은 검토 가설이며 확정 역할 계약이 아니다.

## 2. 1차 자료에서 확인한 근거

### 작업 재개 단서는 단순 상태보다 풍부해야 한다

[Parnin·DeLine, CHI 2010](https://www.microsoft.com/en-us/research/?p=159976)은 개발자 371명의 중단·재개 전략을 조사하고, 자동 재개 단서 두 종류를 메모만 사용하는 조건과 비교했다. 집계형 표현과 시간순 코드 조각 표현 모두 해당 실험에서 도움이 됐으며, 참가자들은 시간순 표현을 선호했다. [저자 공개 논문](https://chrisparnin.me/pdf/cues-chi09.pdf)은 최근 항목을 먼저 보고 과거 행동을 더 거슬러 보는 사용을 설명한다.

이 연구가 모든 로그를 최신순으로 보여야 한다거나 현대 AI 감독 UX에서 같은 성과가 나온다는 뜻은 아니다. mast에 적용할 가설은 “최근 변화로 재진입한 뒤 필요한 이전 사건을 이어서 복원할 수 있어야 한다”이다. 에이전트가 계속 일하는 동안의 감독은 개발자가 직접 중단한 작업을 재개하는 상황과 다르므로 별도 검증이 필요하다.

### 다른 팀원의 의도와 설계 이유를 알아야 한다

[Ko·DeLine·Venolia, ICSE 2007](https://www.microsoft.com/en-us/research/publication/information-needs-in-collocated-software-development-teams/)은 개발자 17명의 활동 관찰에서 정보 요구 21종류를 정리했다. 동료·산출물의 상황을 자주 찾았고, 왜 그렇게 설계했는지 같은 질문은 지식 보유자의 부재 때문에 미뤄지기도 했다.

mast에 대한 설계 추론: 완료 결과만 저장하면 “왜 이 방향인가”를 다시 팀장에게 물어야 한다. 사용자가 승인한 방향과 근거를 일의 결과에 연결해 남기는 것이 중요하다. 인간 팀 연구가 AI 보고의 정확성을 보장하는 것은 아니다.

### AI는 이전 상호작용과 행동 결과를 설명할 수 있어야 한다

[Microsoft Human-AI Interaction Guidelines](https://www.microsoft.com/en-us/research/articles/guidelines-for-human-ai-interaction-eighteen-best-practices-for-human-centered-ai-design/)는 맥락에 맞는 정보, 최근 상호작용 기억, 행동 이유와 사용자 행동의 결과 설명, 오류 교정을 권고한다.

적용 가설: “B안을 선택했다”와 “그 결과 새 의존성이 생겼다”를 함께 보여야 한다. 사용자가 말하지 않은 이유를 모델이 그럴듯하게 보충해서는 안 된다. 잘못된 보고는 원문을 확인하고 교정할 경로가 필요하다.

### Linear도 상태 외에 활동·질문·사용자 입력을 구별한다

[Linear Agent Interaction](https://linear.app/developers/agent-interaction)은 세션 상태와 별도로 질문, 행동, 응답, 오류, 사용자 입력을 표현한다. [Best Practices](https://linear.app/developers/agent-best-practices)는 대화 복원에 편집 가능한 댓글보다 특정 시점의 입력을 보존하는 활동 기록을 쓰도록 안내한다.

mast에 대한 시사점은 화면 모양을 복제하는 것이 아니라, 질문과 답변을 상태 문자열로 합쳐 없애지 않는 것이다. 이 API 존재만으로 Linear의 화면이 사용자의 요구를 충족한다거나 특정 UX가 검증됐다고 주장하지 않는다.

### 총괄 모델의 존재와 좋은 보고 UX는 별개다

[Anthropic의 multi-agent research 사례](https://www.anthropic.com/engineering/multi-agent-research-system)는 lead agent와 전문 작업자의 분담을 설명한다. 독립 작업을 모으는 구조의 실제 사례지만, 병렬 연구 결과를 합치는 문제와 이미 진행 중인 개발팀을 감독하는 문제는 다르다. 총괄 모델을 추가하는 것만으로 기억·전달·검증 문제가 해결된다고 추론하지 않는다.

## 3. 역할과 대화 경로: 검토 가설

| 역할 | 책임 | 기본적으로 보고할 수준 |
| --- | --- | --- |
| 사용자 | 목표·제약·중요 선택·우선순위 결정 | 본인의 결정이 작업에 어떻게 반영됐는지 확인 |
| 워크스페이스 메인 에이전트 | 해당 작업의 실행 조율과 근거 있는 진행 보고 | 방향, 결과, 장애물, 선택지와 영향, 검증 |
| Manager | 여러 작업의 이전 맥락과 새 변화를 연결해 설명하고 요청을 적절한 팀장에게 전달 | 묶음 현황, 필요한 결정, 이전 결정 이후의 변화, 작업 간 관계 |
| 보드 | 사람이 원하는 작업·결정·근거를 직접 찾아가는 지속적인 화면 | 총괄 보고와 개별 작업의 상세 기록 |

추가 팀장 에이전트보다는 기존 메인 오케스트레이터를 작업의 대화 상대라고 식별하는 방식을 우선 검토한다. 모든 pane을 동등한 책임자로 취급하면 리뷰자의 질문과 구현자의 질문이 서로 섞일 수 있다. 메인 에이전트 선택·변경 방식은 미정이다.

보드에 머문 채 두 경로를 제공하는 가설:

1. “매니저에게 전체 질문”: 여러 작업을 묶어 현재 상황과 결정 맥락을 조회한다.
2. “이 작업의 팀장에게”: 특정 작업의 책임 에이전트에게 직접 지시·질문하고 답변을 받는다.

대상은 항상 화면에 보인다. 사용자는 단순 전달에도 매번 긴 총괄 모델 응답을 기다릴 필요가 없어야 한다. Manager가 사용자 결정을 재해석하거나 작업자가 자율 선택한 안을 사용자 승인으로 바꾸어 전달해서는 안 된다.

## 4. 정보 구조 대안

| 대안 | 장점 | 사용자 목적에 대한 위험 |
| --- | --- | --- |
| 상태 목록 + 최신 요약 + 별도 대화 | 스캔이 빠르고 기존 구조에 가깝다 | 원인·결정·실행의 관계를 사용자가 다시 조립해야 한다 |
| 모든 활동을 시간순으로 표시 | 원문과 순서가 보존된다 | 도구 출력·반복 보고가 늘어 읽기 부담이 커진다 |
| 현재 보고 + 의미 있는 사건별 경과 + 원문 근거 | 짧은 재진입과 상세 복원을 함께 지원할 가능성 | 사건 연결이 틀리거나 중요한 예외가 숨겨질 수 있어 검증 필요 |

세 번째를 우선 검토하되, 목록/카드/상하 분할 같은 시각적 형태는 아직 고정하지 않는다.

### 전체 보드에서 복원할 것

각 작업은 이름과 상태뿐 아니라 다음 네 질문에 답해야 한다.

- 왜 시작했고 어떤 결과를 원했는가?
- 사용자가 마지막으로 정한 중요한 방향은 무엇인가?
- 그 뒤 무엇이 바뀌었는가?
- 지금 어느 단계이고 사용자가 판단할 것이 있는가?

내용을 모두 한 화면에 무조건 펼치는 것이 목표는 아니다. 전 작업을 스캔하는 밀도와 선택한 작업을 이해하는 깊이를 나누되, 상세 진입 후에도 핵심 관계가 분리된 탭에 흩어지지 않게 검토한다. 사용자가 마지막으로 확인한 이후의 변화는 재진입 지점 후보이며, 보드를 열었다는 이유만으로 읽음 처리하는 방식은 검증이 필요하다.

### 작업 상세에서 복원할 것

“계기와 지시 → 중요한 질문과 선택지 → 사용자의 선택 → 그 선택에 따른 실행과 결과 → 새 질문 또는 현재 단계”의 연결을 보여 준다. 이를 개별 채팅 버블이나 전체 이벤트 수로 표현할 필요는 없다. 같은 결정을 다룬 질문·답·실행을 한 덩어리로 읽을 수 있는지 확인한다.

한 사건의 요약을 펼치면 실제 사용자 발언, 팀장 보고, 관련 변경·검증 근거를 볼 수 있어야 한다. 마지막 단계에서 전체 transcript나 해당 pane으로 이동한다. 모든 상세 확인을 pane 이동으로 떠넘기면 목적을 충족하지 못한다.

## 5. 보고 예시: 외부 라이브러리 선택

아래는 UX 검토용 가상 사례이며 실제 mast 작업 기록이 아니다.

**작업: 대용량 로그 내보내기 개선 — 검증 중**

- 시작 이유: 큰 로그를 저장하면 앱이 멈춰 사용자가 결과를 받지 못했다.
- 지시: 기존 파일 형식은 유지하고 메모리 급증을 줄여 달라고 했다.
- 중요한 질문: 팀장이 표준 기능으로 스트리밍할지, 외부 라이브러리를 추가할지 물었다. 라이브러리는 구현이 간단하지만 의존성이 늘어난다는 비교를 보고했다.
- 사용자 결정: “이번에는 의존성을 늘리지 말고 표준 기능으로 진행해.”
- 이후 작업: 청크 단위 저장을 적용했고 기본 테스트가 통과했다.
- 새로 드러난 점: 대용량 검증 중 취소하면 임시 파일이 남았다. 완료를 보고할 단계는 아니다.
- 지금 필요한 판단: 취소 시 즉시 삭제할지, 재개를 위해 남길지 결정해야 한다. 팀장은 임시 파일 삭제를 추천하며 재개 기능은 별도 범위라고 설명한다.

총괄 보고의 예:

> 로그 내보내기는 의존성을 추가하지 않는 방향으로 구현했습니다. 기본 테스트는 통과했고, 대용량 취소 검증에서 임시 파일이 남는 문제가 나왔습니다. 기존 결정은 유지되며 취소 파일 처리만 추가 결정이 필요합니다. 삭제를 추천하고 있습니다.

작업 상세에서는 비교했던 A/B안, 사용자의 원래 답, 실제 적용 결과와 검증 내역을 각각 펼칠 수 있어야 한다. “B안 완료, 테스트 중”만으로 압축하면 의사결정에 필요한 맥락이 사라진다.

## 6. 기억과 근거에 미치는 영향

최신 세 필드는 개요 표시에는 재사용할 수 있지만, 덮어쓰기만으로 질문·답·실행 연결을 신뢰성 있게 복원하기 어렵다. 짧은 보고와 보존할 사건을 구분하는 방향을 검토한다.

- 작업 시작 이유와 최초 지시.
- 중요한 질문, 제안한 선택지와 근거, 답한 사용자 및 원문, 변경된 결정.
- 그 결정이 반영된 실행 보고와 검증 결과.
- 보고 주체, 시점, 원문/산출물 참조, 수집이 끊긴 지점.

임의로 모든 로그를 영구 저장하거나 새로운 범용 메모리 시스템을 만들기로 한 것은 아니다. 기존 transcript와 이벤트를 활용해 무엇을 안정적으로 연결할 수 있는지 검토가 먼저다. 질문 ID가 없는 입력이나 모순된 보고는 확인되지 않은 연결로 남겨야 한다.

사용자가 방향을 번복하면 이전 결정은 과거 맥락으로 남기고 현재 유효한 결정은 명확히 구분한다. 팀장이 보고한 “완료”와 검증 도구가 확인한 결과를 구별한다. running/idle 같은 프로세스 상태만으로 구현 중/테스트 중을 단정하지 않는다.

## 7. 사용성 검증안

핵심 지표는 클릭 수나 요약 길이가 아니라 **충분히 이해한 상태로 다음 판단에 도달하는 시간과 정확도**다.

동일한 기록을 세 대안에 넣고 화면 순서를 바꿔 비교한다. 사용자가 직접 했던 작업과 처음 보는 작업을 구분한다. 6~10개 작업 사이에 다른 일을 끼워 넣고 다시 돌아오는 상황을 사용한다.

측정 질문:

1. 이 작업은 왜 시작했고 범위에서 제외한 것은 무엇인가?
2. 내가 어떤 안을 선택했고, 에이전트가 실제로 그 안을 따랐는가?
3. 지금 필요한 결정은 이전 질문과 어떻게 다른가?
4. 구현 완료와 검증 완료 중 어디까지 확인됐는가?
5. 다음 지시를 어느 팀장에게 보내야 하는가?

측정값: 정답에 도달한 시간, 잘못 기억한 결정 수, 과거 대화 재탐색 횟수, 팀장에게 반복 질문한 횟수, 원문을 열어야 했던 이유, 잘못된 대상에게 입력한 횟수. 원문을 열었다는 사실만으로 실패로 계산하지 않는다. 필요한 근거 확인과 요약 불충분으로 인한 탐색을 구분한다.

## 8. 다음 검토

## 9. Fable 독립 검토 반영 (2026-10-04)

Fable의 결과 파일과 인용한 요약 추출·전송 경계 코드를 직접 대조했다. 실행 기록은 `.bare/harness-runs/2026-10-03-manager-context-ux/fable/`에 있으며, 아래에 판단을 남긴다. 추가 인용 중 Fable이 서지·미확인으로 표시한 연구는 검증된 실증 근거로 승격하지 않는다.

### 채택할 조사 방향

1. **사용자의 마지막 관여를 보고 기준점으로 삼는다.** 단순 최신 상태보다 “내가 결정한 것 → 그 뒤의 변화 → 지금 필요한 판단”이 재진입 단서가 된다. 마지막 답변과 마지막 확인은 다를 수 있으므로 상세 기준은 미정이다.
2. **중요한 안건을 연결해 보여 준다.** 질문·선택지·사용자의 답·그 결과·후속 질문을 한 묶음으로 복원한다. 최초 지시와 판단이 필요 없었던 진행도 기록하므로 모든 작업을 의사결정 안건으로 억지 변환하지 않는다.
3. **브리핑 → 작업 경과 → 근거 발췌의 깊이를 제공한다.** 원문 확인을 전부 터미널로 떠넘기지 않는다. 원문 전체는 마지막 탐색 수단이다.
4. **팀장이 자율적으로 정한 중요한 변경도 보고한다.** 의존성·공개 계약·범위 변경 등은 사용자 판단에 영향을 줄 수 있다. 현재 추출 경로는 셸·파일 도구 출력을 버리므로, 발화에 없는 변경까지 포착했다고 보장할 수 없다.
5. **UX와 정보 추출의 충실도를 따로 검증한다.** 잘 쓴 더미로 복원 시간이 줄어도 실제 모델이 질문·조건·번복을 잘못 연결하면 제품은 실패한다.

### 수정하거나 보류한 제안

- 역할 이름을 반드시 “총괄 보좌”로 바꿀 필요는 없다. 사용자가 말한 총괄 팀장 비유를 유지하면서, 합의한 실행 범위와 사용자 결정권을 명확히 하면 된다. 이름만으로 자율 권한을 확대하거나 축소하지 않는다.
- 모든 문장에 출처 배지를 노출하면 보고가 다시 장황해진다. 중요한 주장·불확실성은 기본 화면에서 구별하되 상세 출처 표시는 펼쳤을 때 읽는 방안을 검토한다.
- 명시적인 사용자 전달 지시마다 추가 확인 버튼을 요구하지 않는다. 대상·범위가 불명확하거나 원래 요청과 의미가 달라지는 경우에만 확인이 필요하다. 이미 허용된 입력 전달을 다시 승인받는 절차로 만들지 않는다.
- 전송 기록을 transcript만으로 대체하는 제안은 채택하지 않는다. 도착하지 않은 메시지는 transcript에 없으므로 전송 시도·실패·수신 확인을 추적할 최소 기록이 별도로 필요하다.
- “언급 없음”은 “하지 않음”과 다르다. 테스트 미실행이 명시된 경우와 기록이 없어 실행 여부를 모르는 경우를 구분한다.
- 첫 에이전트 pane을 자동으로 팀장으로 확정하는 것은 보류한다. 생성 순서만으로 책임자를 추정하면 잘못 전달할 수 있다.
- 현재 기록만으로 과거 작업 전체의 시작 이유나 암묵 결정을 복원할 수 있다고 주장하지 않는다. 기존 작업 연결 시 누락을 보여 주고 필요한 원문을 추가 조회하는 경로가 필요하다.

### 이번 위임에서 발견한 전달 경계 문제

`mast id`는 환경변수 `MAST_TAB`을 출력하고, `mast ls`와 `mast send`는 실제 터미널로 OSC를 보낸다. 코어는 실제 송신 세션의 워크스페이스로 조회·전송 범위를 제한한다. main과 manager 브랜치 모두 이 제한을 유지한다.

이번 환경에서는 `MAST_TAB=26`인데 `mast ls`의 자기 자신 표시가 `#14 *`였고, 조회된 워크스페이스는 `dxf 자동화`였다. #100도 그 워크스페이스에 있었다. 이는 워크스페이스 간 전송 지원의 증거가 아니라 환경의 논리적 탭 ID와 실제 전송 경로가 어긋난 관측이다. 환경에는 `MAST_TTY=/dev/ttys004`가 설정돼 있으나, 어느 시점에 어떤 이유로 불일치했는지는 확정하지 않았다.

Fable 요청은 #100에서 수신·완료되고 결과 파일이 남았다. 회신 대상은 환경변수에서 가져온 #26이었다. 이 불일치가 회신 미도착을 설명할 가능성이 있지만 실제 회신 라우팅 실패는 검증하지 않았다. 추가 전송·환경 수정은 하지 않는다. 향후 중앙 전달 UX에도 표시 대상과 실제 송신·수신 정체성을 검증하는 문제가 포함된다.
