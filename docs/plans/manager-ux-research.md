# Manager UX 개선 조사와 화면 검토안

- 작성일: 2026-10-03
- 대상: `feature/manager-workspace`
- 상태: 조사·브레인스토밍 기록. 아래 합의 사항 외 설계는 제안이며, 제품 구현 승인이 아니다.
- 화면 초안: [mast 앱 내부 Manager 더미](../prototypes/manager-workspace.html). 사용자는 이 초안이 컨텍스트 복원 요구를 충족하지 못한다고 평가했다. 승인된 화면이 아니다.
- 후속 조사: [여러 작업 감독과 컨텍스트 복원](manager-context-recovery-research.md). 아래 화면 제안은 이전 검토 기록이며, 새 사용자 설명을 반영한 후속 조사를 우선한다.

## 1. 사용자 문제와 목적

기존 보드는 여러 pane의 내용을 모아 둔 것처럼 느껴졌고, 답변이 장황해서 전체 진행 상황을 파악하기 어려웠다. 사용자가 원하는 것은 각 작업의 정제된 진행 상황, 본인의 입력, 에이전트의 핵심 답변, 중요한 결정과 맥락이다. 긴 원문은 해당 pane에서 확인할 수 있으므로 보드에서 반복할 필요가 없다.

매니저와 대화하며 여러 작업을 관리할 수 있어야 한다. 현재처럼 요약을 읽고 설명하는 역할만으로는 기대한 효용이 부족하다. 화면 개선과 함께 기억의 구성, 입력 전달, 상태의 근거를 검토한다.

## 2. 합의한 사항

| 항목 | 사용자와 합의한 내용 |
| --- | --- |
| 완성도 | 개인용 MVP부터 실제 사용으로 검증 |
| 작업 단위 | 우선 워크스페이스 1개를 작업 1개로 취급 |
| 매니저 역할 | 작업 생성, 입력 전달, 맥락 조회, 후속 행동 제안 |
| 사용자 결정 | 우선순위 변경과 실행 중단 |
| 기존 작업 | 매니저가 생성하지 않은 기존 워크스페이스도 연결 |
| 수동 pane 추가 | 사용자가 +로 추가한 pane도 소속 워크스페이스의 작업에 연결 |
| 현재 요청 | 조사 문서와 실제 mast 앱 구조를 반영한 HTML 더미 작성 |

워크스페이스 단위를 선택한 뒤 사용자는 MVP 편의뿐 아니라 실제 개발자 UX에서 적절한지 조사해 달라고 요청했다. 다음 절은 그 조사와 추천이며, 예외 처리와 세부 수명주기는 아직 확정하지 않았다.

## 3. 확인한 현재 구조

2026-10-03 manager 워크트리의 파일을 읽었다. 워크트리에는 기존 미커밋 변경이 있으므로 이 기록을 HEAD 전체에 대한 감사나 실행 검증으로 해석하지 않는다.

- [ADR-0032의 v2 개정](../adr/0032-manager-workspace-preview.md): 워크스페이스별 최신 요약 하나를 교체한다. `progress`, `needs_input`, `next`의 상한은 각각 400·600·600자다. 이전 요약과 새 발화가 다음 요약의 입력이다.
- [저장·매니저 안내](../../scripts/wsl/mast-manager.py): 요약 식별자는 경로와 배포판에 기반한다. 매니저 안내는 다른 탭에 입력하거나 워크스페이스를 생성·전환하는 행동을 금지한다. 현재 안내가 사용자가 기대하는 관리 권한과 다르다.
- [요약 프롬프트](../../scripts/wsl/mast-manager-harness.py): 진행 필드에 유효한 결정과 제약도 보존하도록 요구한다. 화면 요약과 맥락 보존이 같은 좁은 필드에서 경쟁한다.
- [보드 뷰](../../apps/mast/src/features/manager/board-view.ts): 레포 그룹, 요약 필드, 경로 설정과 이동 동작을 제공한다. 사용자의 목표·입력·결정 이력을 구분해 읽는 화면은 부족하다.
- [사이드바](../../apps/mast/src/features/workspace/sidebar.ts): 일반 워크스페이스 카드와 별도로 하단 New workspace 위에 Manager를 고정한다.
- [스타일](../../apps/mast/src/app/styles.css): 기본 배경 `#1e1e1e`, 패널 `#252526`, 테두리 `#3c3c3c`, 활성색 `#007acc`. 사이드바는 220px이며 pane마다 얇은 탭바와 테두리를 가진다.
- [실제 앱 참고 이미지](../image/mast-desktop-mobile.png): 사이드바와 분할 터미널이 중심이다. 별도 웹 서비스의 대형 헤더·내비게이션을 추가하면 기존 앱 경험과 어긋난다.

이 구조에서 요약을 더 줄이면 맥락이 빠지고, 맥락을 보존하면 카드가 길어질 가능성이 있다. 이는 코드 구조에 근거한 해석이며, 실제 사용자 오류율을 측정한 결과는 아니다.

## 4. 개발자 UX 조사: 어떤 단위가 적절한가

### 공식 제품 사례

| 제품 | 단위와 동작 | 시사점 |
| --- | --- | --- |
| [VS Code](https://code.visualstudio.com/docs/editing/workspaces/workspaces) | 워크스페이스는 창에서 열린 하나 이상의 폴더이며 설정과 UI 상태를 보관 | 프로젝트 환경을 묶는 의미로도 널리 쓰이므로 용어 자체가 작업을 뜻하지는 않는다 |
| [cmux](https://cmux.com/docs/concepts) | 워크스페이스 안에 pane, 그 안에 surface를 둔다 | 실행 화면의 계층이며 특정 업무 단위를 강제하지 않는다 |
| [Conductor](https://www.conductor.build/docs/concepts/parallel-agents) | 독립적으로 반영할 작업은 별도 워크스페이스, 같은 브랜치·코드·맥락을 공유하는 에이전트는 같은 워크스페이스 | 목표 하나에 여러 에이전트를 모으는 설계의 실제 사례 |
| [Conductor worktrees](https://www.conductor.build/docs/concepts/git-worktrees) | 워크스페이스별 worktree와 브랜치에 대화·검토 흐름 연결 | 화면 단위와 파일 격리를 함께 설계하되, 둘은 별개의 기능임을 주의 |
| [Mylyn](https://help.eclipse.org/latest/topic/org.eclipse.mylyn.help.ui/Mylyn/FAQ/Task-Focused-UI.html) | 작업별 맥락으로 관련 정보에 집중하고 작업 간 전환 지원 | 중요한 것은 터미널 개수보다 작업 맥락의 복원 |

### 연구의 근거와 한계

[Mylyn 연구진의 회고 및 현장 연구 설명](https://link.springer.com/chapter/10.1007/978-1-4842-4221-6_24)에서는 모집 99명 중 분석 기준을 만족한 16명의 사용 전후를 비교했고, 도구 사용 후 탐색 대비 편집 활동 비율이 개선됐다고 보고한다. 작업별 맥락 복원의 가치를 뒷받침하지만, 현대 멀티에이전트 터미널에서 워크스페이스와 작업의 1:1 관계가 모든 대안보다 우수하다는 증거는 아니다.

### 단위 비교와 추천

| 단위 | 장점 | 한계 |
| --- | --- | --- |
| pane 또는 에이전트 세션 = 작업 | 실행 대상이 직접 보임 | 같은 목표의 구현·리뷰·테스트가 분산되고 세션 재시작 때 연속성이 끊김 |
| 프로젝트 = 작업 | 기존 IDE 사용 습관과 친숙 | 병행하는 여러 목표의 상태와 결정이 섞임 |
| 작업을 워크스페이스와 별도 관리 | 여러 환경을 오가는 장기 업무에 유연 | 별도 객체와 연결 관계를 관리하는 부담 |
| 워크스페이스 = 완료할 목표 하나 | 전환 시 관련 pane과 맥락을 함께 볼 수 있음 | 작업의 크기, 공용 터미널, 보관·복원 정책이 필요 |

mast에는 마지막 방식을 추천한다. 작업은 명령이나 체크리스트 항목이 아니라 **독립적으로 진행·검토·완료할 수 있는 목표**로 정의한다. 이 결론은 제품 사례와 시나리오에 근거한 설계 판단이다.

- 로그인 오류 조사·수정·리뷰·테스트: 한 워크스페이스, 여러 pane.
- 로그인 오류 수정과 내보내기 성능 개선: 독립적인 두 워크스페이스.
- 컨텍스트 소진으로 에이전트 재시작: 같은 워크스페이스에서 계속.
- 프론트와 백엔드가 같은 목표를 위해 함께 바뀜: 같은 워크스페이스를 허용. 레포 수만으로 작업을 나누지 않음.
- 각각 독립적으로 출시하는 변경: 분리 권장.
- 상시 서버·로그·임시 셸: 작업 보드 제외를 제안하되 사용자 확인 필요.

사용자 안내는 “워크스페이스 하나에 완료할 목표 하나. 구현·리뷰·테스트 pane은 그 안에 추가하세요”가 적절하다. 이름은 `Claude`나 프로젝트명보다 `로그인 오류 수정`처럼 목표를 드러내도록 유도한다. 이를 강제하는 유효성 검사나 모든 사용자별 설정 옵션은 이번 범위에 넣지 않는다.

## 5. 화면 제안

### 실제 mast 안에서의 구성

기존 앱의 사이드바와 pane 크롬을 유지한다. 하단 고정 Manager를 선택하면 상단 보드 pane과 하단 매니저 대화 pane을 볼 수 있는 분할 구성을 초안으로 제시한다. 이는 기존의 단일 pane 내 보드/터미널 탭 구성과 다른 **검토용 배치 제안**이다.

보드 내부 왼쪽은 작업 목록, 오른쪽은 선택한 작업의 상세다. 작업 목록은 한 워크스페이스당 한 행이며 작업명·상태·마지막 변화·필요한 행동만 표시한다. 레포는 보조 정보로 둔다. 선택 시 목표, 최근 답변, 사용자 입력과 주요 내역을 보여 준다. 긴 원문은 실제 작업 pane으로 이동해 읽는다.

하단 매니저 대화에서는 작업 전체 질문과 후속 행동 제안을 처리한다. 작업 상세의 입력창은 현재 작업의 특정 pane으로 보내는 지시에 사용한다. 대상 pane을 명시해서 전체 매니저에게 하는 요청과 혼동하지 않게 한다.

### 정제된 답변 계약 제안

| 상황 | 기본 표시 |
| --- | --- |
| 진행 | 바뀐 점 하나와 다음 행동 |
| 질문 | 결정할 내용, 선택지, 추천과 이유 |
| 완료 보고 | 결과, 검증 여부, 남은 문제 |
| 실패 | 원인, 영향, 필요한 조치 |

글자 수를 줄이면서 미검증·실패·사용자 결정 조건을 제거하지 않는다. 여러 pane의 서로 다른 질문은 각각 대상과 함께 보존해야 한다. 완료 보고를 검증 통과와 동일하게 표시하지 않는다.

[점진적 공개 원칙](https://www.nngroup.com/articles/progressive-disclosure/)에 따라 기본 화면은 짧게, 세부 맥락은 선택 후 펼친다. 여러 작업을 읽어야 하는 첫 화면에 긴 대화나 전체 이력을 반복하지 않는다.

## 6. 메모리·컨텍스트 제안

화면용 요약을 유일한 기억으로 쓰지 않는다.

| 구분 | 보존할 내용 |
| --- | --- |
| 작업 기준 | 목표, 범위, 완료 조건, 확정한 제약 |
| 현재 상태 | 단계, 장애물, 미답변 질문, 다음 행동 |
| 주요 이력 | 사용자 지시·답변, 결정 변경, 결과와 검증 근거 |
| 화면용 요약 | 위 정보를 읽기 쉽게 표현한 짧은 문구 |

사용자 입력은 원문과 요약을 구분한다. 결정 변경은 대체 관계를 남긴다. pane에서 직접 내린 지시도 같은 작업에 반영해야 한다. 다른 pane이 오래된 결정을 말했을 때 최신 사용자 결정을 덮어쓰지 않는 규칙이 필요하다.

매니저는 전체 작업의 짧은 색인을 보고 관련 작업의 기록만 추가 조회한다. 원문은 참조를 통해 필요할 때 읽는다. [Anthropic의 컨텍스트 설계 자료](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)는 외부 구조화 기록과 필요한 시점의 조회를 설명한다. 이 자료가 특정 저장 제품이나 스키마 선택을 확정하는 것은 아니다.

벡터 DB, 지식 그래프, v1 원장의 전면 복구는 현재 제안하지 않는다. 워크스페이스의 지속적인 식별자와 기억을 연결하는 방향은 검토하되, 현재 숫자 ID를 재시작·닫힘·복원 후에도 그대로 사용할 수 있는지는 별도 확인한다. 경로가 같아도 서로 다른 작업일 수 있고 경로가 바뀌어도 같은 작업일 수 있다.

## 7. 매니저 행동과 신뢰

- “내 답변이 필요한 작업만 보여줘”: 질문과 대상 작업을 조회.
- “이 작업은 A안으로 진행하라고 전달해”: 지정한 pane으로 사용자 지시 전달.
- “어제 정한 범위와 달라진 게 있어?”: 결정 이력과 현재 보고 비교.
- “새 세션에서 이어가게 정리해”: 목표·확정 결정·미해결 사항을 조회해 인계 내용 제안.
- “다음에 뭘 확인하면 좋을까?”: 후속 행동을 추천. 우선순위 변경이나 중단을 자동 실행하지 않음.

입력은 전송 시도, 수신 확인, 답변 반영을 구별한다. 전송 API 성공만으로 수신이나 실행 완료를 표시하지 않는다. 사용자가 입력한 동안 질문이나 대상 세션이 바뀐 경우의 처리도 정해야 한다. 상태 집계와 정렬은 코드가, 의미 요약과 판단은 모델이 맡는 구성을 우선 검토한다.

## 8. 검증 제안과 미결정 사항

다음 수치는 실제 측정 결과가 아니라 사용성 검증 목표다.

- 작업 8개 중 답변이 필요한 일을 10초 안에 찾는다.
- 하루 뒤 돌아와 30초 안에 목표·마지막 결정·다음 행동을 파악한다.
- 보드 입력이 어느 pane에 전달됐고 어디까지 확인됐는지 구별한다.
- 세션을 다시 시작해도 확정 제약과 미답변 질문을 잃지 않는다.
- 오래된 요약·실패·미검증 완료를 현재 사실로 오해하지 않는다.
- 같은 작업의 수동 pane 추가가 별도 작업으로 중복 등록되지 않는다.

열린 질문:

1. 보드와 대화의 상하 분할, 좌우 분할, 탭 전환 중 실제 사용에 편한 배치.
2. 일반 워크스페이스의 보드 제외와 신규 워크스페이스 기본 포함 정책.
3. 닫기·완료·보관·복원을 구분하는 UX와 기록 수명.
4. 여러 pane의 질문·결정 충돌, 입력 대상 선택, 수신 확인 방법.
5. 기억의 식별자, 기존 v2 데이터 처리, 원문 보존량과 삭제 정책.
6. 요약 비용·지연 허용치와 지원 에이전트 범위.
7. 같은 디렉터리에서 여러 작업을 진행할 때 worktree 격리를 어디까지 지원할지.

이번 산출물은 이 질문을 검토할 문서와 더미다. 제품 코드, 영구 에이전트 지침, 저장 계약을 변경하지 않는다. 구현 계획 확정과 구현 승인은 별도이며, 완료 전 ADR의 accepted 상태로 기록하지 않는다.

## 9. 더미 검토 방법

[HTML](../prototypes/manager-workspace.html)을 브라우저에서 직접 연다. 네트워크 호출·실제 에이전트 실행·mast 상태 변경·영구 저장은 없다. 새로고침하면 예시로 돌아간다.

- Manager 고정 카드: 보드와 매니저 대화로 복귀.
- 일반 워크스페이스 카드 또는 상세의 pane 열기: 예시 분할 터미널로 이동.
- 보드의 작업 행: 요약·맥락·이력 확인.
- 연결된 pane의 +: 같은 작업에 예시 pane 추가.
- 입력 전달: 전송 시도만 예시 이력에 기록.
- 하단 대화의 예시 질문: 전체 작업 기준의 정제된 응답 확인.
- 새 작업: 예시 워크스페이스와 보드 행 생성.

실제 테마와 계층을 참고한 제안 화면이며, 실행 중인 mast의 스크린샷이나 구현 완료 화면이 아니다. 자동 브라우저에서 로컬 HTML을 여는 것은 브라우저 정책상 차단되어 시각 검증을 완료하지 못했다. JavaScript 문법, 문서의 로컬 링크, 정적 HTML ID 중복, 외부 요청 부재를 확인했다. Happy DOM에서 초기 보드, 작업 pane 이동, Manager 복귀, 수동 pane 연결, 전송 시도 기록, 매니저 상태 반영, 새 워크스페이스 생성의 7개 상호작용을 확인했다. 레이아웃·스크롤·가독성은 실제 브라우저에서 별도 검토해야 한다.
